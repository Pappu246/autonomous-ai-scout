## Consistency and fencing contract

1. **Atomic submission:** a caller-generated idempotency key, an immutable digest over the canonical request, mission, queue and optional approval proposal (including authorization and completion-criteria digests and approval/output requirements), the mission, and any proposal row commit together. A retry with the same key and identical content returns the existing IDs; any changed request, payload, approval action, expiry or proposal conflicts. Approval-required submissions have *no* runnable queue row before approval; the original queue payload is stored separately and restored transactionally at activation. Callers may pass `approval_action_id`, `approval_expires_at`, and `approval_payload` to `submit()` to atomically create the pending approval row with the mission. Do not derive keys from task text or allow untrusted content to choose grants.
2. **Worker claims:** `SELECT ... FOR UPDATE SKIP LOCKED` selects pending rows; the same transaction marks the queue **and** mission running with a monotonically increased `claim_generation`. Heartbeat and completion require the task, execution, worker and generation to match. PostgreSQL row locks are transaction-scoped: a crashed session rolls back and releases its lock. There is **no client-side owner GET followed by an unconditional lease DELETE**.
3. **Recovery:** stale heartbeats can advance the generation and atomically move queue and mission to `recovery_required`, with an audit event. They are **never automatically re-enqueued**. A disconnected/stalled former worker cannot complete or update state. A still-running external side effect cannot be un-done; an authorized operator must reconcile before a new attempt, with new execution identity and approval as necessary. PostgreSQL commit acknowledgement loss is reported as **unknown**, not retried blindly; reconcile by idempotency/event ID and database state.
4. **Approvals:** proposal rows belong to missions already requiring approval. Only an independently authorized API may decide one. The adapter stores a digest (not the raw token), enforces pending → approved/rejected and expiry against database time, and consumes an approved token while inserting the **single** queue item in the *same transaction*. Crash-after-consume cannot issue a second runnable item; crash-before-commit leaves it unconsumed. This is at-most-one database activation, **not exactly-once external effects**.
5. **Timeline and memory:** immutable, uniquely identified events form a per-mission hash chain serialized by an audit-head row lock. A bounded MVCC-snapshot read verifies sequence, hashes and the head. Completing a claim changes queue and mission, appends its terminal event, and stores episode memory in one transaction. VERIFIED requires a matching validated output audit digest for output-requiring requests or a verified tool-result event for an explicit read; it does not replace the existing output validator/authorization policy. Runtime roles must lack `UPDATE`/`DELETE` on audit events and memories. A database administrator or compromised writer can still tamper; the chain is not a substitute for off-site audit retention.
6. **Isolation:** all keys include an explicit Preview namespace. Every Preview branch needs a unique approved namespace or a deliberate shared-coordinator policy. The old Blob branch key mapping is not a migration; old deployments and workers must be retired/reconciled before any new writes. The adapter never reads/writes Blob or unguarded local JSON as an authoritative fallback.

The implemented adapter is a **native transactional API**, not a file-lock shim. This matters: the existing execution checkpoint and parts of audit replay read/write files outside `InterProcessFileLock`; merely wrapping a JSON file with a DB lock would leave stale or per-container state. The checkpoint adapter now persists schema-v2 checkpoint metadata per `(namespace, task, execution, claim generation)`, verifies the live worker claim before reads/writes, and rejects changed task/plan/authorization digests or regressing progress. A `PostgresExecutionCheckpointStore` bridge now implements the execution-engine checkpoint contract, and the engine/core/runtime APIs accept an explicitly injected checkpoint store while preserving the local JSON default. A claim-fenced `PostgresExecutionAuditStore` now appends execution events into the mission hash chain and can be explicitly injected through the same execution path. These are narrow checkpoint/audit seams only: the caller must still provide a live claim, the runtime readiness gate remains closed on Vercel, and run journal, approvals, mission rows and memory are not migrated. A PostgreSQL `run_journal` table/API now stores bounded result records keyed by claim generation; terminal journal records commit atomically with mission state and memory and must match the terminal outcome; only recovery-required records can be written separately under a live claim. A local-only `PostgresMissionRunner` now composes DB submission, fenced claim, execution with PostgreSQL audit/checkpoint stores, evidence validation, and atomic terminal+journal+memory commit for autonomous local read-only plans. Its real-PostgreSQL E2E tests exercise the complete read-only slice outside Vercel/Blob mode, including output/memory verification, unsafe-task rejection, idempotency conflicts, failed reads, and the hosted gate; it deliberately rejects network/mutation/approval plans and calls the existing hosted readiness gate. During a long-running read-only execution, it now refreshes the claim heartbeat. A heartbeat failure stops the runner from writing terminal state, run-journal or memory records and leaves the running attempt for explicit reconciliation; regression tests cover both periodic heartbeat and fail-closed heartbeat loss. It is **not wired into the hosted HTTP `MissionController`**. The legacy `MissionController` is **not yet migrated** to the API. SQL-level component tests therefore do **not** certify hosted workflow execution. A future integration must replace *every* queue, mission, approval, claim, checkpoint, journal, timeline and memory call site, preserve policy/output validation, and prove end-to-end behavior before clearing the fail-closed gate. This is the remaining application work, not a configurable toggle.
