## Threat model and source map (baseline)

- `vercel.json` rewrites only `/`, `/login`, `/logout`, `/health`, `/api/missions` and nested mission/approval API routes through `gateway_next` to `runtime_next`; `Dockerfile.vercel` and `Dockerfile` build separate Python containers. `api/proxy.py` is a legacy Vercel function path; the Services gateway is `autonomous_agent/vercel_gateway_server.py` + `vercel_proxy.py`. Historical Azure instructions in `docs/DEPLOYMENT_VERCEL_AZURE.md` are not the current deployed Services architecture and should not be followed as current instructions.
- `vercel_proxy.py` enforces an HTTPS backend origin, bounded route allowlist, no upstream redirects, body/response size limits, no browser cookie forwarding, and no proxy request logging. Preview uses Vercel edge SSO instead of the application's token-collection form. Non-Preview fallback login accepts only the separate workspace token and sets a Secure/HttpOnly/SameSite=Strict cookie. The backend `server.py` requires `SCOUT_SERVER_TOKEN` on non-loopback binds and returns path-free `/health`; loopback is unauthenticated by design. Live edge protection is a **deployment setting**, not proof supplied by `VERCEL_ENV=preview` alone.
- The source HTML pages are generated by the gateway/runtime, link only to the public GitHub repository, and have no third-party runtime script/CDN or software-download link in the inspected source. The browser-visible Vercel SSO page is supplied by Vercel, not by this repo. Source inspection cannot rule out altered older deployments or authenticated dynamic content. Do not attribute Google's classification solely to the former workspace login without affected-URL evidence.
- Queue, mission metadata, approvals, audit, and memory are JSON files in `/app/state`, synchronized to private Vercel Blob through `InterProcessFileLock`/`VercelBlobStateSync`. The queue worker executes only after claiming a persisted item; `MissionController` mediates planning, grants, approval, execution, memory and timeline. Vercel Blob is a required integration for hosted durability, not a guarantee against every race or regional outage.

## Findings ranked at baseline

1. **High — FAILED (configuration/visibility):** Three credential-bearing environment variables are Config/`encrypted` and readable to authorized project members; the screenshot's `Needs Attention` label is consistent with Vercel's security recommendation but the exact card finding was not read. This is *not* proof that any value is publicly exposed. No variable has been changed. Owner-approved provider-supported migration/rotation and environment scoping are required.
2. **High — VERIFIED (Google-side classification):** The exact host remains unsafe in Google's official status. Why Google classified it, which URL(s), and whether the existing report is being reviewed remain **BLOCKED**. Edge SSO now prevents unauthenticated access to the previous workspace password page, but that is separate from Google's verdict.
3. **High — source finding pending reproduction:** `MissionController.activate_approved_action` and `resume` expose a new queue item before persisting the mission record for its new `task_id`; a worker can claim it first. That can leave mission history/status detached from execution. See remediation report for deterministic race test.
4. **Medium — source finding pending reproduction:** Fallback login uses the actual workspace credential as the session cookie; the server does not independently enforce the cookie's 12-hour lifetime. A copied cookie could be replayed until token rotation even after its browser expiry; application logout clears only the browser copy. Confirm and test a bounded opaque session before changing code.
5. **Medium — source finding pending reproduction:** Gateway `_reply` always sends `Cache-Control: no-store`, but `_proxy` also forwards the backend's `Cache-Control`, which can produce conflicting headers. The proxy should unconditionally prevent caching of mission/approval responses.
6. **Medium — source finding pending reproduction:** `MissionController` records `partial` for a missing-provider project-summary task while the queue worker marks the item `failed`; `partial` is absent from terminal/resumable states. This can strand a partial mission despite honest content.
7. **Medium — NOT TESTED:** Shared Blob keys use `VERCEL_ENV=preview` only, not a Preview branch namespace; different Preview branches with the same Blob resource would share queue, memory, approvals and history. Any key migration needs a history-preserving plan and owner approval; do not silently strand current records.
8. **Medium — NOT TESTED:** Blob leases rely on 120-second stale timing, not an ownership-fenced conditional write; prolonged operations and concurrent recovery can create ownership ambiguity. Similarly, stale running task recovery uses a fixed 600-second threshold without periodic worker heartbeat. These need controlled fault/concurrency testing before claiming exactly-once execution.
9. **Medium — BLOCKED:** No authenticated live Preview session, Blob runtime logs, deployment-protection bypass inventory, or Google Search Console Security Issues access was available; end-to-end deployment verification is therefore blocked. Neither green CI nor READY metadata substitutes for these tests.

## Stage 2 forensic addendum (2026-10-17)

The baseline list above is deliberately historical. A successful `filesystem.read` was demonstrated to mark a two-fact-summary request VERIFIED without producing **any** summary; a negated instruction could also select an unrelated tool. Stage 2 now derives a bounded requested-output contract, validates a two-fact extractive artifact against an authorized full read/fingerprint, persists it through mission/API/memory, and otherwise returns `partial` rather than a false success. It cannot provide arbitrary model-written analysis, and neither tool success nor untrusted file text authorizes actions.

Deterministic local red/green probes also exposed duplicate decided approval IDs, silent approval-queue overflow, stale worker/queue completion on reclaimed attempts, stale DAG progress and inventory fallback, memory overwrite across identical tasks/attempts, Blob transaction publication after a raised body, and a workspace-read path into `state/` or `.env.*` plus generic token disclosure. The scoped code/test changes address those local cases. **A separate isolated fake-Blob interleaving still reproduces an unresolved distributed race:** one owner checks its lease, another replaces the lease, and the first owner's unconditional `delete` removes it. Blob's unconditioned overwrite/delete cannot establish a fenced lock; cross-instance atomicity/once-only side effects remain **NOT VERIFIED/BLOCKED**, not fixed by this addendum. See the remediation report for precise tests and release gates.

## Stage 3 coordination finding and containment (2026-10-17)

**FAILED**: two red interleaving regressions against PR #282's earlier Blob lease implementation confirmed both release and stale-reaper time-of-check/time-of-use races. The installed pinned `vercel==0.11.6` source sends `x-allow-overwrite: 0` on create-only PUT; GET's `if_none_match` is read-only; `BlobClient.delete` accepts URL(s) and token only and sends unconditional POST `/delete`. This offers no conditional delete/ETag/version or monotonically fenced state write. A client-side owner string cannot repair it. No project setting or credential visibility change turns this into a transactional lock; Vercel Services do not provide a verified cross-deployment singleton/persistent shared file system in this audit.

**VERIFIED locally as fail-closed containment, not distributed execution:** the review code removes the Blob lease mutation path, refuses hosted/Blob-configured locks before per-container fallback, blocks direct tasks before tools, pauses the hosted worker and returns explicit HTTP 503/unavailable health. Synthetic fault/concurrency tests confirm no SDK calls or state publication during stale leases, competing workers, interrupted local processes, retries or failed cleanup. Single-host file locking remains available only in local mode without Vercel/Blob markers. Old READY deployments still run their own older code and require owner-controlled retirement; this new code cannot retroactively fence them. A durable transactional coordinator with conditional/fenced writes across all stores, or an enforceable exclusive single-writer deployment with durable disk and no overlapping versions, is required before hosted E2E. **No exactly-once claim.** At published safety-code SHA `70bea7b...`, GitHub CI/container/Windows checks succeeded, but Vercel's commit status failed with “Deployment rate limited — retry in 24 hours”; no READY Preview maps to this gate. See `E2E_VALIDATION.md` for exact run links. The separate `autonomous-scout-state` `MISSING_SERVICES` errors are not the cause of this rate limit or evidence about PR #282's code.
